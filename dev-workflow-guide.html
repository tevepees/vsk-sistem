Memahami Staging vs Production

Panduan visual untuk Tony — bagaimana kita memisahkan ruang "tes" dari ruang "live" di sistem VSK, kapan deploy ke mana, dan workflow harian yang aman untuk pemula SDLC.

1
Konsep dasar — staging itu apa?

Bayangkan sebuah restoran. Production = dapur asli yang menyajikan ke pelanggan. Staging = dapur latihan yang setup-nya sama persis tapi tidak ada pelanggan. Koki uji resep baru di dapur latihan dulu — kalau enak, baru dipakai di dapur asli.

Staging

Lab tes

  • Hostname mengandung kata staging
  • Database terpisah (spreadsheet [Staging])
  • Boleh rusak, boleh ada bug, boleh data kacau
  • Dipakai untuk uji fitur baru sebelum dipakai operator
Production

Live

  • Hostname tanpa kata staging
  • Database utama (spreadsheet asli)
  • Tidak boleh rusak — operator pabrik pakai ini
  • Hanya menerima fitur yang sudah lulus tes di staging

Kenapa ini penting?

Tanpa staging: kalau ada bug di kode baru, langsung kena ke operator pabrik. Data produksi harian bisa rusak, susah di-recover. Staging = jaring pengaman — kamu coba dulu di sana, baru promote ke production saat yakin aman.

3
Workflow harian — cara kerja yang aman

Setiap kali kamu mau update sesuatu (fix bug, tambah fitur, ganti warna), ikuti 5 langkah ini. Tidak ada step yang bisa di-skip kalau kamu mau aman.

1

Pindah ke branch staging

Pastikan kamu kerja di branch staging, bukan main. Branch main hanya untuk kode yang sudah lulus tes.

git checkout staging
2

Edit kode, commit, push

Buat perubahan yang kamu mau (mis. tambah fitur). Commit dengan pesan jelas, lalu push.

# di terminal, di folder repo
git add .
git commit -m "tambah field catatan di kedatangan"
git push origin staging
3

Deploy ke staging worker

Kirim kode ke Cloudflare Workers — target staging. Tunggu sampai selesai (biasanya <30 detik).

npx wrangler deploy --env staging
4

Buka URL staging, test sungguh-sungguh

Buka vsk-sistem-staging.workers.dev di browser. Coba semua skenario yang relevan: input shift, timbang karung, switch modul, dst. Pastikan tidak ada error di console (F12 → Console). Kalau ada bug, balik ke step 2.

⚠ Test di staging WAJIB. Kalau di-skip, bug bisa lolos ke production.

5

Promote ke production: merge & deploy

Setelah yakin staging stabil, gabungkan branch staging ke main, lalu deploy ke production worker.

git checkout main
git merge staging
git push origin main
npx wrangler deploy --env production
4
Cheat sheet — perintah yang sering dipakai

Print atau bookmark halaman ini. Kalau ragu, balik kemari.

# ─── Setup awal (sekali saja per komputer) ─── $ git clone https://github.com/tevepees/vsk-sistem.git $ cd vsk-sistem $ npm install -g wrangler $ wrangler login # ─── Mulai kerja: pindah ke staging ─── $ git checkout staging $ git pull # ─── Setelah edit kode ─── $ git status # cek file mana yang berubah $ git add . $ git commit -m "deskripsi perubahan" $ git push origin staging # ─── Deploy STAGING (uji coba) ─── $ npx wrangler deploy --env staging # ─── Deploy PRODUCTION (live, hati-hati!) ─── $ git checkout main $ git merge staging $ git push origin main $ npx wrangler deploy --env production # ─── Lihat log live (kalau ada error di prod) ─── $ npx wrangler tail --env production
5
FAQ untuk pemula SDLC
Bagaimana kalau salah deploy ke production?
Jangan panik. Kalau code di branch main sebelum perubahan masih bagus, kamu bisa git revert dan deploy ulang. Lebih aman lagi: sebelum deploy prod, pastikan branch main isinya identik dengan apa yang sudah lulus uji di staging.
Kenapa harus 2 branch? Kenapa bukan langsung edit di main?
Karena branch main = kontrak dengan production. Setiap commit di sana harusnya artinya "kode ini sudah lulus tes". Kalau langsung edit, semua eksperimen ada di sejarah main — dan kalau lupa, satu push tidak sengaja bisa rusakkan production.
Apa beda --env staging dan --env production?
Cuma flag — tapi flag inilah yang menentukan worker mana yang di-update. --env staging kirim ke vsk-sistem-staging, --env production kirim ke vsk-sistem. Kalau lupa flag, wrangler akan tanya / error. Sengaja begitu supaya kamu tidak salah target.
Apakah perlu deploy backend (Apps Script) tiap kali?
Tidak — frontend dan backend deploy-nya terpisah. Backend Apps Script v6 sudah live di kedua spreadsheet. Yang sering kamu deploy adalah frontend (HTML/CSS/JS via wrangler). Backend di-update hanya kalau kamu ubah file VSK_AppsScript_v6.js — itu lewat Google Apps Script editor, bukan wrangler.
Kalau mau coba di laptop tanpa deploy, bisa?
Bisa. Buka file index.html langsung di browser (double-click). Karena hostname jadi localhost atau file://, env detection akan auto-pilih staging. Tidak perlu deploy apa-apa untuk preview UI.
Kapan harus update versi service worker (sw.js)?
Setiap kali ada perubahan besar di frontend yang kamu mau pastikan user terima fresh, naikkan const CACHE = 'vsk-sistem-vN' ke versi berikutnya (v1 → v2). Browser akan invalidate cache lama otomatis.
